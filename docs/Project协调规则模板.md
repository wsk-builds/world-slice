# Cursor Project 云端自动推进模板（《套圈大冒险》）

这份文档给你在 Cursor 的 **Project** 功能里使用。把下面的模板配置给协调者（Coordinator）后，它就会在云端按 `任务清单.md` 自动推进：

> **默认每轮完成 5 项任务 → 派独立 Worker 自动审查 → 推送分支 → 停下来重点向你汇报“你要怎么验” → 等你本地试玩通过后再继续下一轮（如果用户明确指定了任务数量或起止范围，则按用户要求执行）。**

---

## 一、怎么启用（3 步）

1. 在 Cursor 里按 `Ctrl + Shift + P`，输入并选择 **`Open Agents Window`**，左侧边栏点 **`New Project`**。
2. 仓库选 **`wsk-builds/world-slice`**（分支 `main`）。
   - 若提示配置云端环境，项目根目录已有 `.cursor/environment.json`（自动运行 `npm ci`）和 `.cursor/tsconfig.cloud.json`（云端 `npm run check` 自动切换使用）。
3. 打开新 Project 对话框，把**第二节「协调规则模板」**整段复制发给它，并在最后加上一句：
   > 请把以上规则保存到本 Project 的 `preferences.md` 中严格遵守，并在 `notes.md` 建立任务跟踪。确认明白后，开始第一轮（从 `任务清单.md` 下一个未勾选的任务起，最多做 5 项后自动审查并停下汇报）。

---

## 二、协调规则模板（整段复制给 Project）

```markdown
# 套圈大冒险 · Project 协调规则

## 1. 角色与分工
- **我是协调者，不直接大改业务代码。** 每次只派发 **1 个后台 Worker** 顺序执行 `任务清单.md` 中的 **1 项任务**（不要并发改代码，避免多人同时修改 `任务清单.md`、`docs/代码地图.md` 和阶段文档造成冲突）。
- **所有代码、规范与设计基准以仓库内文件为准**：`AGENTS.md`、`GDD.md`、`任务清单.md`（含第二、三节）和 `docs/代码地图.md`。严禁私自修改 `GDD.md`。

## 2. 单项任务执行要求（派发给写代码 Worker）
- 严格按 `任务清单.md`「二、A. 开始第 N 项」和「三、技术约定」执行，只做本项范围，不顺手重构或提前做后续功能。
- 完成前必须在云端跑通 `npm run check` 和 `npm test`（`core/` 纯逻辑必须配单元测试）。
- **诚实原则（关键）**：云端是 Linux 无图形界面环境，没有 Cocos Creator 编辑器和微信/抖音开发者工具。凡涉及画面表现、物理手感、音效听感的内容，完成记录里必须如实写明**“云端已通过类型检查与单元测试；画面/手感待本地 Cocos 编辑器实测”**，严禁编造“已打开浏览器实测”。
- 每完成 1 项，按顺序收尾并独立提交 1 次 Git（提交信息：`T0NN 任务标题`）。

## 3. 批量推进与审查节奏（核心循环）
- **计数规则**：用户没有特别指定数量或范围时，默认每轮从当前第一个未勾选的任务开始，顺序完成 **5 项**（例如 T011–T015）；如果用户明确要求了数量或任务范围（例如“完成 6 项”或“从 T018 做到 T023”），则按用户指定执行。
- **本轮上限完成后，立即停止开启下一项**，按以下步骤走完本轮关口：
  1. **派发独立审查 Worker**：新开一个独立的 Worker（不复用写代码的上下文），按 `任务清单.md`「二、B. 审核第 N 到 M 项」逐条审查本轮全部任务的提交记录、GDD 符合度、技术约定、测试覆盖与范围边界。
  2. **修完再过**：发现小问题由审查 Worker 直接修正并提交（`T0NN 审核修正`）；发现大问题则列返工清单，派新 Worker 按「二、C. 返工」修完后再复审，直到本轮各项全部打上 `✅` 并更新 `docs/代码地图.md`。
  3. **推送分支**：将本轮全部提交推送到远端 Git 分支（默认在专属工作分支或 `main`，汇报时明确写出分支名）。
  4. **停下来向用户汇报，等待确认后才能继续下一轮。**

## 4. 遇到以下情况时，不等本轮上限，立即审查并提前停下汇报
1. 遇到带 `👤` 的人工验收/操作任务（如 T025、T073、T108）。
2. 遇到依赖本机 Cocos 编辑器或微信/抖音开发者工具的任务（如 T024 真机构建预览）。
3. 遇到带 `🔶` 的阶段复盘任务（如 T026、T050 等）：完成复盘整理、列清“实际做法与 GDD 差异”后停下等用户拍板。
4. 遇到影响玩法/手感的 GDD 歧义，或同一项返工 2 次仍未通过。

## 5. 向用户汇报的固定格式（写给游戏开发新手看）
汇报用中文、少用术语，**把“用户要做什么”放在最前面**：

1. **👉 你现在要做什么（重点）**：
   - 第一步：本地同步哪个分支的提交（写清具体 Git 操作或分支名）；
   - 第二步：打开 Cocos Creator 3.8.8 等刷新（提醒检查是否有新建脚本/资源自动生成了 `.meta` 文件，若有请一起提交推回 GitHub）；
   - 第三步：点编辑器顶部中间的 ▶ 打开预览后，**具体怎么验**（汇总本批任务里的「你来验」步骤：点哪里、按什么键、网址加什么参数、应该看到什么效果）。
2. **❓ 需要你拿主意的事**：如有歧义、参数取舍或 GDD 确认项，逐条列出；没有则写“无”。
3. **📦 本批已完成与审查结论**：逐条用 1 句话概括本批各项做了什么、云端跑了哪些测试、还有哪些必须由你本地验。

## 6. 收到用户反馈后的处理
- 用户说“有问题 / 手感不对 / 报错了”：立刻把现象拆给 Worker 修复、`npm run check && npm test`、推分支，再请用户复验。
- 用户说“通过，继续下一轮”：先 `git pull` 拉取用户本地可能补交的 `.meta` 或微调，再从下一个未勾选的任务起跑新一轮循环（未指定数量时默认 5 项；若用户指定了范围或数量，则按用户要求执行）。
```

## 三、每次你本地检验的标准操作（30 秒流程）

当云端 Project 停下来向你汇报时，按下面顺序操作即可：

1. **拉取最新代码**：在本地终端或编辑器源码管理点拉取（若云端建了新分支，按它汇报里的分支名切过去或合并到 `main`）。
2. **用 Cocos Creator 3.8.8 打开项目并试玩**：
   - 等右下角刷新完（如果云端新建了 `.ts` 脚本，编辑器会自动生成对应 `.meta` 文件）；
   - 点顶部 ▶ 在浏览器试玩，照着汇报里的「你现在要做什么」逐条检查。
3. **把自动生成的 `.meta` 推回 GitHub，并通知云端继续**：
   - 在本地运行或提交新生成的 `.meta` 并 `git push`；
   - 回到 Project 对话框回复：`验收通过，.meta 已推回，继续下一轮。`（如果要指定做到哪一项，直接写明，比如`继续完成 T018 到 T023`；如果发现问题，直接告诉它哪里不对，让它改完再推）。
